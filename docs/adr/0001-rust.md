# 0001 — Implementation language: Rust

- Status: Accepted
- Date: 2026-10-30

## Context

The hot path is: decode (external), scale, encode escape sequences, write to a tty.
That is CPU-bound, allocation-sensitive, and must run identically on Linux, macOS and
Windows. We also want a credible open-source project that contributors can build with
one command.

Candidates: Rust, C, C++, Go, Zig.

## Decision

Rust (edition 2024, stable toolchain, MSRV tracked in `Cargo.toml`).

## Consequences

- Strong crates for the exact pieces we need: `fast_image_resize` (SIMD scaling),
  `crossterm` (terminal control), `criterion` (benchmarks), `symphonia`/`cpal` (audio,
  M4), `axum` (server, M5), `thiserror`/`anyhow` (errors).
- `#![forbid(unsafe_code)]` is realistic for our crates: no manual memory management,
  no buffer-overflow class of bugs in a parser that eats untrusted manifests.
- Cross-compilation and static binaries are straightforward for release packaging.
- Cost: FFmpeg bindings are painful on Windows, which drives ADR 0002 (sidecar first).
- Cost: compile times are worse than C/Go; mitigated by a thin dependency set and
  `cargo check` in the inner loop.

## Alternatives considered

- **C/C++**: best library ecosystem for media (libav, notcurses) but manual memory
  safety in a network-facing parser is a liability, and Windows builds are worse.
- **Go**: excellent DX and cross-compilation, but the graphics hot path wants SIMD and
  zero-GC behavior; cgo for libav removes most of Go's advantages.
- **Zig**: interesting for control over allocation, but the ecosystem (image scaling,
  HTTP server, testing) is immature for a 1.0.
